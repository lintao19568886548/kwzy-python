# 工作台自动化迁移与切换 Runbook

## 门禁

执行真实迁移前，数据负责人必须提供经授权的旧 schema dump、脱敏样本、tenant/customer 映射、用户映射、时区、消息高水位和 XXL-Job 清单；业务负责人需签字确认事件/通知保留期与未知类型处置。缺任一项均保持 `BLOCKED`。生产停写、切换、回滚和删除均需单独人工授权。

## 演练顺序

1. 在隔离 PostgreSQL 16 恢复脱敏快照，只读校验 `event_outbox`、`event_consume_log`、`in_app_notification` 和任务配置的字段、行数、最早/最晚时间与重复键。
2. 固化 tenant、park、user 映射；未知映射进入隔离清单，不创建占位用户、园区或接收人。
3. 运行 dry-run，拒绝未知状态、重复幂等键、孤儿消费记录、完整手机号/邮箱和未注册 handler/event。
4. 先迁用户/RBAC/园区授权，再迁可映射事件、消费证据和通知；任务定义一律以停用状态导入。
5. 从新系统业务原始表重建合同到期、审批逾期等来源 WorkItem；旧 `api_log` 不生成待办或布局。
6. 重跑同一批次，确认插入数为零；模拟中断后确认事务无部分行。
7. 对账：按 tenant、事件类型、状态、接收人、日期和幂等键核对；`SUCCEEDED` 不得多于源成功证据，隔离数必须逐条可追溯。
8. 在影子环境启动至少两个 `python -m app.workers.workbench` 副本，验证 `SKIP LOCKED`、无重复 action、失败重试、DEAD、重放、超时恢复和重启续跑。
9. 浏览器按管理层、园区经理、业务人员验证默认/角色/个人布局、站内消息、下钻、403/409、离线与重试。
10. 备份新库并完成删除测试库、恢复、唯一 Alembic head、关键行数和 worker 再启动验证。

## 获批切换步骤

1. 冻结旧规则和 XXL-Job 配置变更，记录配置校验和与负责人。
2. 停止旧系统新增 Outbox，等待可重试消息排空；记录每租户高水位、DEAD 和未映射清单。
3. 执行最后增量抽取、幂等载入与全量对账；任何 P0/P1 或数目不一致立即停止。
4. 启动新 API 和 `workbench-worker`，先保持迁入调度定义停用；人工复核后逐项启用。
5. 开放 PC 流量，观察事件最老年龄、PENDING/RETRY/DEAD、任务失败率、连接池和 API p95。
6. 保留旧系统只读窗口和回滚备份，直到业务签字完成。

## 回滚

- 停止新 worker 和写流量，不删除新库。
- 按已记录高水位恢复旧发布/调度；只回放旧系统未确认成功的消息。
- 对新系统切换窗口内产生的业务写入生成补偿清单，由各业务负责人审批；禁止反向猜测状态。
- 恢复前一备份并重新执行迁移 head、约束、行数和审计链校验。
