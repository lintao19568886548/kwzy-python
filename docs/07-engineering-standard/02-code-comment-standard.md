# 02 代码注释规范（Code Comment Standard）

> 状态：**正式冻结**  
> 语言：注释与 docstring **以中文为主**（标识符保持英文）

---

## 1. 目标

1. 让后人 3 分钟内理解「做什么、为何做、边界在哪」。  
2. 业务规则写进 docstring，避免只存在于口头或旧 Java 脑内。  
3. 与日志、异常、测试描述用语一致。  

---

## 2. 必须注释的对象

| 对象 | 是否必须 docstring |
| --- | --- |
| 所有 `class` | **必须** |
| 所有模块级 `function` / `def` | **必须** |
| 核心业务方法（Service / Domain / Repository 公共方法） | **必须** |
| interface 路由处理函数 | **必须**（可简写，但字段齐全） |
| 私有方法 `_foo` | 建议；含业务分支时 **必须** |
| 常量/枚举业务含义 | 建议一行说明 |
| 明显的一行 getter | 可简化，但公共 API 仍建议完整格式 |

---

## 3. 标准格式（强制模板）

所有强制 docstring 使用下列中文段落（可省略「无」的段落，但标题建议保留）：

```text
功能说明：
    <一句话说明做什么>

业务职责：
    <在领域/用例中的角色；属于哪一层>

输入参数：
    <参数名>：<含义、约束、单位、是否可空>

返回结果：
    <结构、成功语义；分页字段说明>

异常说明：
    <异常类型/业务 code>：<何时抛出>

业务规则：
    <不变量、状态限制、权限、租户/园区约束>
```

### 3.1 Python 示例（规范形态，非本阶段实现代码）

```python
class ParkService:
    """功能说明：
        园区应用服务，编排园区创建/修改/查询用例。

    业务职责：
        应用层；协调仓储与领域状态校验，不直接暴露 HTTP。
    """

    def create_park(self, data: dict) -> dict:
        """功能说明：
            在当前租户下创建园区。

        业务职责：
            应用层用例；写入 parks 并返回统一字典结构。

        输入参数：
            data：园区字段字典；name 必填；status 默认 ACTIVE。

        返回结果：
            含 id/tenant_id/name/status 等字段的 dict。

        异常说明：
            AppError(VALIDATION_ERROR)：名称为空。
            AppError(PARK_SCOPE_DENIED)：无园区权限时由仓储抛出（如适用）。

        业务规则：
            1. tenant_id 必须来自 TenantContext，禁止信任客户端伪造。
            2. 软删除园区不在本方法恢复。
            3. 状态必须属于 ACTIVE/INACTIVE。
        """
```

---

## 4. 分层注释侧重点

| 层 | docstring 侧重 |
| --- | --- |
| interface | 对应 HTTP 路径、鉴权、入参校验、响应 envelope |
| application | 用例步骤、事务、调用了哪些仓储/领域规则 |
| domain | 不变量、状态迁移表、禁止事项 |
| infrastructure | 表/查询意图、tenant/park 过滤如何施加、性能注意点 |

---

## 5. 行内注释规范

**允许：**

- 非显而易见的「为什么」  
- 与旧系统兼容点、迁移债、临时开关  
- 安全注意（权限、串租风险）  

**禁止：**

- 复述代码字面意思（`# 循环列表`）  
- 大段历史吐槽无结论  
- 过期 TODO 不标注负责人与日期  

TODO 格式：

```text
# TODO(phase06-party, 2026-08-07): 登录支持 tenant_code 消歧
```

---

## 6. 模块文件头（建议）

每个业务 `.py` 文件顶部：

```python
"""功能说明：
    <本文件在模块中的职责>

业务职责：
    <所属层与限界上下文>
"""
```

---

## 7. 命名与注释一致性

| 要求 |
| --- |
| docstring 中的业务名词与领域统一语言一致（园区/入驻方/收款登记等） |
| 禁止把 Payment 写成「在线支付下单」 |
| 禁止把 is_overdue 写成 status=OVERDUE |

---

## 8. 审查门禁

PR 检查：

1. 新增 public class/function 无中文 docstring → 打回  
2. 核心 Service 方法缺「业务规则」段 → 打回  
3. docstring 与实现明显不符 → 打回  

---

## 9. 冻结声明

自本规范生效起，**新提交代码必须符合本注释标准**。  
Step1 历史代码可在触碰文件时顺带补齐，不要求一次性重写全库。
