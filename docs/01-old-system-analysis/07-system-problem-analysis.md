# 07 旧系统问题诊断

> 视角：CTO / 架构师 / DDD / 智慧园区产品  
> 原则：指出问题与影响，不贬低迁移期工程取舍；为 Python 重建设定「必须还的债」

---

## 一、代码问题

### 1.1 模块耦合

| 现象 | 证据 | 影响 |
| --- | --- | --- |
| 薪酬挂在租赁包 | `rental/tenant` 含 Salary* API | 领域边界错乱，改合同易伤工资 |
| 账单服务依赖核验/园区/短信证明 | `AmountBillService` 多依赖 | 单测与演进困难 |
| 招商 Controller 巨型化 | `InvestmentController` 1000+ 行 | 冲突率高、评审难 |
| 财务同步散落 | `FinanceLedgerSyncService` 被多处调用 | 账务入口不唯一 |
| messaging 类爆炸 | 大量 *PlanService / DryRun* | 认知负荷极高 |

**结论：** 技术分包按业务域的方向正确，但 **域内边界与跨域依赖未治理**。

### 1.2 分层混乱

| 现象 | 影响 |
| --- | --- |
| 迁移期以 JdbcTemplate SQL 为主，MyBatis-Plus 空转 | 双 ORM 心智 |
| Controller 兼容旧文案/旧路径 | 业务规则渗入接口层 |
| Repository 内含权限与 schema 探测 | 数据访问层过重 |
| 大量 `Map<String,Object>` 进出 | 无类型契约，重构危险 |
| 缺少清晰 Domain Model / 聚合根 | 规则散落 if-else |

### 1.3 重复代码

- 各模块「鉴权 → 取租户库 → 解析园区 scope → 查页」样板重复  
- maintenance 多资产 CRUD 高度同构  
- access 子资源重复模式  
- 前端 PC/Mobile 双份页面  

### 1.4 命名与语义债

- `investment_tenant` 不像租户  
- `salary` 在 rental 路径  
- `magic` 作为库名/历史产品名与品牌「易租维」不一致  
- 中英文/拼音混用路径（`hygieneCheck`、`factoryMaint`）

### 1.5 测试与质量

- 存在测试 Controller，业务自动化测试覆盖未知且迁移期难保证  
- 生产日志级 JDBC DEBUG 配置风险（`application.yml` 中 JdbcTemplate DEBUG）  
- Feature Toggle 过多导致「同版本不同行为」

### 1.6 安全与配置

- 未使用完整 Spring Security 链，安全靠自定义 Filter  
- 内部接口依赖 token，开关矩阵复杂  
- 密钥全靠环境变量（正确）但本地误配易启动失败/弱保护  
- 公开登记类接口需持续防刷审计

## 二、业务问题

### 2.1 流程不清晰

| 业务 | 问题 |
| --- | --- |
| 入驻 | 招商转化与直接建档两套入口，无统一入驻单 |
| 合同 | 无版本/变更/退租结算闭环 |
| 收费 | 以「填收款时间」代替完整收款单 |
| 催缴 | 有发送能力，无催缴策略与工单 |
| 核验 | 与账单状态关系约定化，非强流程 |
| 客户 | 线索/租户/企微客户三套身份 |

### 2.2 数据模型不合理

1. **租户主体与合同合体**（`rental_tenant`）—— 续租、多合同、换房难  
2. **账单宽表费项**—— 新费项改表  
3. **收款状态用 receipt_time 空否表达**—— 部分收、坏账、减免难  
4. **used_area 与合同占用可漂移**  
5. **客户主数据缺失**  
6. **财务非复式、无核销关系**  

### 2.3 产品能力落差（智慧园区期望 vs 现状）

| 期望能力 | 现状 |
| --- | --- |
| 物联网自动出账 | 有表计集成，主路径仍人工/导入 |
| 线上缴租 | 支付能力偏会员，非租金收银台 |
| 统一工单 | 多表巡检，标准工单弱 |
| 空间数字化 | 到楼层，缺铺位/CAD/地图深度 |
| AI 园区助手 | 有客服/识别，未形成运营 Copilot 闭环 |

### 2.4 运营体验问题

- 菜单与路由来源多（静态+动态），用户可能看到不一致  
- 移动端功能全但页面双维护，体验易分叉  
- 账单三管道强大但学习成本高

## 三、架构问题

### 3.1 单体问题

- **单 Spring Boot 进程承载**：交易、导入、爬虫配置、AI、支付、HRM、MQ 消费  
- 某模块（账单导入/雷达）资源尖峰会拖垮全体  
- 发布粒度粗，局部改动全量回归  

### 3.2 数据库问题

| 问题 | 影响 |
| --- | --- |
| 一客户一库 | 隔离强，运维/迁移/跨租户分析成本高 |
| schema 漂移兼容 | 运行期探测 information_schema，性能与确定性差 |
| 缺外键与枚举约束 | 脏数据靠应用 |
| 中心/租户双写用户 | 一致性风险 |
| dump 与线上不一致 | 新环境难复现 |
| 分析查询打交易库 | 看板拖慢业务 |

### 3.3 扩展困难

- 新费项、新合同类型、新审批流往往要加列加接口  
- 雷达与核心租赁同库同应用，扩展互相干扰  
- 多租户中间件自研，团队新人成本高（虽有 project-guide）  

### 3.4 消息与任务架构

- Kafka + Rabbit + XXL-Job + Spring Schedule 并存，职责需专家脑内建模  
- Outbox 正确，但通知链路开关过多，接近「配置驱动状态机」  
- 不利于 Python 侧简单复刻，应抽象而非翻译  

### 3.5 前端架构

- monorepo 优秀，但业务代码与 Vben demo 共存噪音大  
- 类型与 API 不同步  
- 三端靠同一套页面堆 mobile 分支，长期难维护  

### 3.6 迁移架构本身的债务

旧系统是 **Node Nitro → Java Spring Boot** 迁移态：

- 成功点：接口兼容、灰度开关、多租户保留  
- 债务：兼容层成为永久层；Map DTO；双路径 API；部分逻辑注释仍指 Nitro  

**若 Python 再 1:1 翻译，将继承三代债。**

## 四、问题优先级矩阵

| 优先级 | 问题 | 理由 |
| --- | --- | --- |
| P0 | 合同/租户/账单领域模型不清晰 | 核心现金流与数据正确性 |
| P0 | 客户主数据分裂 | 招商-入驻-收费断链 |
| P0 | 多租户与园区权限需正确继承 | 产品根基 |
| P1 | 财务入账无统一入口 | 对账与审计 |

| P1 | API 无 OpenAPI 契约 | 三端协作 |
| P2 | messaging 类爆炸 | 可维护性 |
| P2 | 前端双页面 | 成本 |
| P2 | 命名与路径不统一 | 体验与研发效率 |

## 五、风险清单（上线/重构视角）

1. **账单历史金额与财务流水不一致** 导致迁移对账失败  
2. **租户库数量大** 导致连接池与迁移窗口失控  
3. **催缴/短信误发** 合规风险  
4. **公开访客/登记接口** 被刷  
5. **支付回调** 幂等不足导致会员状态错乱  
6. **雷达爬虫** 法律与代理合规风险  

---

## 六、旧系统值得保留的优点

诊断必须公平，下列能力 **新系统应继承**：

1. **中心库 + 租户库** 隔离思路  
2. **园区级数据权限**  
3. **账单三管道**（人工/导入/AI）产品完整度  
4. **Outbox** 可靠事件意识  
5. **高敏操作二次验证**  
6. **PC + App 运营场景覆盖面**  
7. **项目内 project-guide** 文档意识  
8. **Feature Toggle 灰度** 文化（可简化实现）  

---

## 七、诊断结论（一句话）

旧系统是一个 **功能覆盖面优秀、领域模型偏弱、迁移兼容层过厚的智慧园区单体**；  
Python 重建的核心不是换语言，而是 **用 DDD 重切园区运营主链，并把 AI/导入/获客变成可插拔能力**。
